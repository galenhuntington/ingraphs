# Finite four-cycle enumeration, and the new n=17 refuter

## Ready-to-run campaign

The new launcher enumerates the **entire** `cycle:4+4+4+4` family, up to
isomorphism and complementation. It is not a SAT search and has no solver
timeout, copy-count objective, density window, or heuristic pruning.

The pilot ledger is `output/orbital-enum16-20261027.sqlite`. It contains all
30 current n=16 candidates, 64 completed batches (defect weights 0 through
3), and 120,302 distinct hosts, all checked without a new refutation.
Generation took 15.7 seconds and checking 14.6 seconds on three workers.
The native workers themselves used 8.87 summed worker-seconds; Python/SQLite
deduplication and serialization are significant parts of generation time.

A copy of the tested binary is saved as
`output/orbital-enum-worker-20261027`, so ordinary Cargo rebuilds will not
invalidate this campaign's executable fingerprint. Continue with:

```sh
python3 scripts/orbital_enum.py \
    --ledger output/orbital-enum16-20261027.sqlite \
    --binary output/orbital-enum-worker-20261027 \
    --candidates output/batches/all16 --jobs 5 \
    > output/orbital-enum16-complete.csv 2> output/orbital-enum16-complete.log
```

There are **2,336 remaining batches**, containing 38,289,408 assignments.
Do not retain the pilot's `--max-batches 64` when requesting the full run.
The pilot suggests tens of minutes, rather than days; allow an hour for the
first full campaign. This is an extrapolation, not a measured full-run time.
Increasing workers will not linearly speed up the central SQLite writer.
Memory is bounded by small worker batches, not the accumulated library;
the library is stored on disk. The pilot database is about 13 MB. Allow
several hundred MB for the full database, its WAL, and optional exports.

Interrupt with Ctrl-C or SIGTERM and repeat the command to resume. A running,
uncommitted generation batch or check chunk is repeated; completed work is
not. Do not delete the database/WAL files to restart a campaign.

Read-only inspection/export, also usable while the campaign runs:

```sh
python3 scripts/orbital_enum.py --ledger output/orbital-enum16-20261027.sqlite --status
python3 scripts/orbital_enum.py --ledger output/orbital-enum16-20261027.sqlite --export-csv
python3 scripts/orbital_enum.py --ledger output/orbital-enum16-20261027.sqlite --export-library
```

The library export is decimal internal labels, one host per line, readable
by `graphy cull`. These are not the least-decimal public canonical labels.
Changing candidate files or adding `--candidate F` registers additional
candidates; it does not remove old registrations. Each new candidate checks
the existing library from its beginning. `--max-batches 0` skips generation
and just catches up registered candidates against the current library.

Other useful controls:

- `--plan`: register the exact plan/candidates and show selected remaining
  work without spawning workers. Unlike `--status`, this writes the ledger.
- `--max-batches K`: generate at most K **new** batches, then check candidates.
- `--generate-only`: fill the library but do not check candidates yet.
- `--min-defects A --max-defects B`: select a layer interval, preserving
  completed work in other layers. A limited selection is not full coverage.
- `--check-chunk 4096`: bound the host library supplied to each native check.
- `--max-check-chunks K`: bound checking in this invocation, retaining cursors.

For a new installation/ledger, build `cargo build --release --features native`.
SAT is **not required**; `--features native,sat` is also supported. Preserve
that binary if other builds will overwrite it, and pass its path with
`--binary`. A ledger pins both its exact cube plan and the executable SHA-256;
an incompatible binary/plan is rejected, not silently mixed with old results.

This is a **separate ledger**. Never pass either SAT database to this launcher.
It neither imports nor overwrites SAT exclusions, and does not edit `all16`.
Completed generation is not itself an exclusion: the candidate must also
have checked every stored host. Only then does its CSV status become
`family-excluded-by-enumeration`. A partial run reports `partial`, even if
its selected layer interval is finished. A refutation is valid immediately.
None of these outcomes establishes universality outside this family.

## Coverage argument

Let q be two disjoint 8-cycles, and let g=q². The latter has cycle type
4+4+4+4 and generates one C4 action, not four independent C4 actions.

The unordered-pair action of q has 16 orbits, each of even length. Each splits
into two g-orbits. In each pair of g-orbits, specify:

- an orientation bit x;
- a defect bit d: d=0 means the two g-orbits have opposite colors, d=1 means
  they have the same color.

These 32 bits parametrize **all** ordinary g-invariant graphs. The d=0 vector
is a self-complementary subfamily; other defect vectors are not discarded.

Use the vertex permutations which independently rotate the two q-cycles,
optionally exchange them, and multiply both cyclic coordinates by the same
odd unit modulo 8. They normalize q, hence also g. Their induced action on
the 16 defect positions has order 64. There are 2,400 defect-subset orbits;
counts by weight 0 through 16 are:

```
1 4 17 42 98 176 285 370 414 370 285 176 98 42 17 4 1
```

Take one representative defect vector from each orbit. This loses no graph
up to relabeling because all orientations will still be covered.

Global complementation toggles every orientation. Applying q toggles the
orientations in exactly the nondefective positions. If both kinds of position
exist, these operations allow one orientation of **each kind** to be fixed
to zero, independently. Therefore each mixed-defect batch has only 14 free
orientation bits. The two extreme batches have 15 free bits. Total:

```
2398 * 2^14 + 2 * 2^15 = 39,354,368 assignments.
```

This improves on the previous 78,643,200-assignment proposal, which used only
the global-complement reduction of orientation bits. A defect is a broken
relation between two whole edge-orbits, not one flipped edge.

Each batch is an affine cube: a fixed base graph XOR selected disjoint edge
masks. The Rust worker enumerates all assignments in Gray-code order. It
canonicalizes with bundled nauty and identifies complements, choosing the
sparser color first (both native labels are compared when balanced). It
deduplicates locally, and SQLite deduplicates full packed canonical graphs
across batches. These are exact keys, not probabilistic fingerprints.

As a separate check on scale, Burnside's lemma for the full normalizer of g
plus complementation gives 954,508 coloring orbits. Graph isomorphism can
identify additional orbits, so this is an **upper bound**, not a prediction
of the exact final library size. `normalizer_coloring_classes(4)` reproduces
the calculation in `scripts/orbital_enum_families.py`.

## Implementation, validation, and extensibility

Files:

- `src/orbital_enum.rs`: bounded native affine-cube worker; independent of SAT.
- `scripts/orbital_enum_families.py`: deterministic cover and Burnside check.
- `scripts/orbital_enum.py`: library, candidate cursors, transactional resume,
  exclusive writer locking, child cleanup, and read-only exports.
- `scripts/test_orbital_enum.py`: coverage and lifecycle tests.

An unreduced enumeration of all 2^16 assignments for the n=8 four-2-cycle
family produces exactly the same canonical library as the reduced 60-batch
plan. Tests also cover malformed/truncated worker output, ledger/schema
identity, partial negative results, adding candidates without regenerating,
bounded check resume, and SIGTERM cleanup. The n=16 zero-defect batch yields
669 classes and recovers a refuter of 108544687478829056; the independent
Python matcher confirms that positive control in both colors.

Validation completed:

```
cargo test --release --features native,sat                 # 55 tests
python3 -m unittest discover -s scripts -p 'test_*.py'       # 56 tests
cargo check --no-default-features
cargo check --no-default-features --features u64
git diff --check
```

The local SAT-enabled build needed LIBCLANG_PATH pointing to the installed
Nix libclang; the enumeration-only build has no bindgen requirement. No
dependency versions or build flags were changed.

The native worker and durable library/checking machinery are reusable.
The current **cover generator** is specialized to four equal even cycles
(lengths 2 and 4, with n=8 serving as the exhaustive control). Other actions
need their own proved cover and small-case tests; selecting them by changing
a template string is not implemented.

The savings come from the template's many admissible relabelings, not from
requiring a huge automorphism group in each resulting graph. The successful
n=16 refuter itself has only four ordinary automorphisms. Repeated triples
are another plausible beneficiary. Families with few interchangeable parts
may save much less, and a large number of independent color variables can
still make exhaustive generation impractical.

## The n=17 refuter: an augmented four-dimensional cube

The user's new canonical host is

```
338986856409490997648489224340590907136
```

It independently verifies as a refuter of both 221541319920208212992 and
221613518320445584384 (35,396 and 32,324 combined search nodes). Reproduce:

```sh
python3 research/refuter17_structure.py --verify
```

It has 68 edges, degree 8 at every vertex, and 64 automorphisms. It is not
vertex-transitive: its vertex orbits have sizes 8, 8, and 1. It is not the
Paley graph: adjacent pairs have 2, 3, or 5 common neighbors, rather than a
constant value. I have not identified an established name for this graph.

A compact construction labels the vertices A(i,a0,a1), B(j,b0,b1), and z,
with every coordinate binary. There are eight A and eight B vertices.

- A vertices are adjacent exactly when their i coordinates differ: K4,4.
- Distinct B vertices are adjacent exactly when their j coordinates agree:
  two disjoint K4's.
- A(i,a0,a1) and B(j,b0,b1) are adjacent exactly when a_j=b_i.
- z is adjacent to every B and no A.

The cross-edge graph is exactly Q4, independently checked by constructing
binary cube coordinates and testing Hamming distance one for every pair.
The map A(i,a) -> B(i,a), B(j,b) -> A(j,1-b), z -> z complements all edges.
It has cycle type 4+4+4+4+1. The script reconstructs the exact supplied decimal
label, not just an isomorphic version.

The full ordinary group has **10 pair-orbits**, but every cyclic subgroup
has at least **36**. Thus cyclic generation capped below 36 cannot include
it even though its full-group orbital family is tiny. This reinforces the
noncyclic/binary-action direction, without implementing that next portfolio
in this turn.

The script can emit all 1024 assignments of these ten ordinary pair-orbits:

```sh
python3 research/refuter17_structure.py --emit-orbit-unions \
    | graphy-u256 cull 17 output/batches/all17 /dev/stdin
```

This command is for the user's u256 build, which is not on this session's
PATH. It includes the known graph, its complement, and duplicates; at this
size a separate canonicalization pass is unnecessary. It also explores
non-self-complementary members of the family, not only the downloaded set.

I checked all vertex deletions of the supplied graph down to n=16, 15, and
14: respectively 2, 5, and 14 isomorphism/complement classes, with no new
refutations of the current lists. Those deletions need not be repeated.
